### D2. CDS client: ecmwf-datastores-client, used asynchronously
- **Options:** `cdsapi.Client().retrieve()` (blocking), or submit/poll/download by request id with `ecmwf.datastores.Client`, the library `cdsapi 0.7.7` wraps for the current CDS.
- **Evidence:** a blocking retrieve cannot resume a request still queued at the CDS after a restart; the datastores client exposes `submit`, `get_remote(id).status`, `get_results(id).download` and `estimate_costs` (read from the installed source).
- **Choice:** the async path; the CDS request id is stored in the manifest the moment the CDS accepts a request. Credentials are read from `~/.cdsapirc` (mode 600 enforced); the key is never logged or stored. `cdsapi` stays installed.
- **Who:** agent (provisional).

### D3. Column discretisation
- **Choice:** Cₙ² constant per slab between neighbouring valid levels; T_mid = mean of the two levels, P_mid = √(p₁p₂) (log-p midpoint), θ_mid = T_mid(1000/P_mid)^0.286; gradients by finite difference; S² = (Δu/Δz)² + (Δv/Δz)². Levels with p > surface pressure or Z ≤ orography are masked and counted. Non-increasing heights in valid slabs raise an error instead of being repaired.
- **Evidence:** RESEARCH §4.3 prescribes slabs and the log-p midpoint; the rest is our choice.
- **Who:** agent (provisional).

### D4. Troposphere/stratosphere switch for HMNSP99
- **Options:** WMO lapse-rate tropopause with or without a pressure bound; how to handle ERA5's sparse levels near the tropopause.
- **Evidence:** the WMO definition (RESEARCH §4.4). A deep low-level isothermal layer satisfies the WMO criterion without a bound (tested).
- **Choice:** the lowest level with p ≤ **500 hPa** whose lapse rate to the next level is ≤ 2 K/km, and whose average lapse rate to every level within 2 km, and to T linearly interpolated at +2 km, is ≤ 2 K/km. If none is found, all slabs use troposphere coefficients and the column is counted (`tropopause_not_found`). Slabs whose base is at or above the tropopause level use stratosphere coefficients. The 500 hPa bound is our choice and needs checking against the polar winter tropopause *[check]*.
- **Who:** agent (provisional).

### D5. Osborn–Sarazin unstable layers (N² ≤ 0)
- **Options:** `zero` (Cₙ² = 0), `abs` (use |∂θ/∂z|), `nan`.
- **Evidence:** in the stable closed form Cₙ² ∝ S^(4/3) |∂θ/∂z|^(4/3), so Cₙ² → 0 continuously as N² → 0⁺ under both `zero` and `abs`. The O&S paper does not say.
- **Choice:** default `zero`, count firings (`os_unstable_layers`). Compare `zero` and `abs` in the phase 1 ground-layer experiment.
- **Who:** agent (provisional).

### D6. Cloud-above-height overlap
- **Choice:** implement random, maximum and maximum-random (Geleyn & Hollingsworth 1979); default max-random until the phase 1 consistency check (C at the ERA5 surface vs ERA5 `tcc`) picks one. cc outside [0, 1] is clipped and counted; invalid levels count as clear and are counted.
- **Who:** agent (provisional); final rule **[ASK]** with phase 1 evidence.

### D7. O&S ground-layer relocation generalised to any height
- **Choice:** J(h) = I(max(h, z_g + 1 km)) + [I(z_g) − I(z_g + 1 km)], with I(x) = ∫ₓ^top Cₙ² dz. This equals O&S at the site (h ≥ z_g + 1 km), gives the full model column for valley pixels (no double counting), and stays continuous and non-increasing in h (property-tested).
- **Evidence:** O&S §5.4 (relocation of 926–1926 m to 2635–3635 m at Paranal); the split at 1 km is from their §5.7.
- **Who:** agent (provisional); ground-layer treatment itself remains an open **[ASK]**.

### D8. Darkness and the night mask
- **Choice:** Sun GHA and declination from Skyfield (DE440s, SHA-256 pinned), tabulated every 10 min and interpolated (error < 0.5″, tested); geometric altitude, no refraction (as Skyfield's `dark_twilight_day`). Dark minutes counted at minute midpoints of each night window (local mean noon to local mean noon, keyed by evening date). **Ingest night mask:** keep hour t if the Sun is below −12° at any minute in [t − 30 min, t + 30 min), so every hour that touches astronomical darkness is kept with margin (tested).
- **Evidence:** vs Skyfield `almanac.dark_twilight_day` at 9 sites × 6 dates: crossings within 3.7 s, minute counts within 0.96 min.
- **Who:** agent (provisional).

### D9. Unix time → Skyfield time
- **Choice:** pass whole days plus seconds of day to `ts.utc`. `ts.utc(1970, 1, 1, 0, 0, u)` counts leap seconds and lands 27 s early in 2023 (found and tested).
- **Who:** agent.

### D10. Zarr layout for ingested ERA5
- **Options:** one store per request, per month, or per year; append vs write-once.
- **Choice (phase 1):** one Zarr v3 store per manifest request at `/data/astro/era5/{kind}/{region}/{period}.zarr`, written once to a temp directory, read back bit-for-bit, fsynced, renamed, and read back again. Never overwritten (same content → no-op; different content → error). float32 (GRIB is 16-bit packed, so nothing is lost), Blosc zstd level 5 with byte shuffle, chunks ≤ 4 MB with time and level whole, one shard per array (one file per variable per request); the shard is the array shape rounded up to whole chunks, because Zarr v3 needs shards to be multiples of chunks (e.g. 721 latitudes → 23-row chunks → 736-row shard; found in PR review). No consolidated metadata (not in the v3 spec). A `cells` layout (land cells plus a counted night mask) is implemented for phase 2/3. Whether day-sized stores are right for the global run is a phase 2 decision.
- **Who:** agent (provisional).

### D23. Request size: split to the CDS cost limit (amends D16's fallback)
- **Evidence (smoke test, `reports/cds_smoke_test.json`):** the CDS "cost" of a request is its number of fields (variables × levels × hours × days) whatever the area. ECMWF staff define an ERA5 "item" as one variable on one 2-D field at one level and one time step (forum.ecmwf.int/t/cdsapi-limitations-and-restrictions/1639, 2019). Limits today: 60,000 fields for pressure levels, 121,000 for single levels. A month of a 5×5 box on 29 levels × 5 variables is 107,880 fields, over the limit; single levels (12,648) fit.
- **Options:** D16's stated fallback, day-sized requests (31 per month); or split each month into the fewest runs of days under the limit (2 for pressure levels, 1 for single levels).
- **Choice:** split to the limit (`plan_requests(split=True)`, limits in `configs/era5.yaml: request.max_fields`). It keeps D16's aim (few queued jobs) with ~15× fewer requests than daily; content and verification are unchanged. Partial months are now labelled `first_last` (e.g. `2023-01-01_2023-01-16`) so chunks can never share a store path.
- **Who:** agent (provisional); Riley to confirm, since D16's fallback said "day".

### D24. CDS concurrency: at most 4 in flight; queue-limit rejections are transient
- **Evidence:** the first real run submitted 29 requests at once (a downloader bug: `limit=0` meant "no limit"; fixed in fa1c95a with a regression test). The CDS accepted 5 and rejected 24 with "Number queued requests for this dataset is temporarily limited. Please configure your scripts accordingly". Of the 5 accepted, the CDS ran one at a time, and a single-level request submitted while a pressure-level one ran stayed queued for 15 minutes: one running request per user across datasets. The first half-month pressure-level chunk (52,200 fields) ran 1,669 s (31.3 fields/s); the average of the first 9 was 33 min (26.4 fields/s). I found no published per-user limit, so these are observations, not documented limits.
- **Choice:** keep `--max-active 4` (below the observed 5 accepted). A rejection carrying that message sends the request back to `planned` (the remote job is deleted); any other rejection still fails the request. Rejected jobs raise `requests.HTTPError`, not `ProcessingFailedError`; the backend now records the server's message either way (previously the downloader kept polling dead jobs).
- **Who:** agent.

### D39. One CDS job at a time: the downloader's gate, backoff and pause
- **Why:** since 2026-10-22 the CDS wants requests one after another, and it may disable accounts that keep sending invalid ones (forum.ecmwf.int/t/15481; D37). In that thread, a user was disabled with "up to two concurrent monthly requests", so one is a hard limit (Riley, 2026-10-30).
- **Options:** (a) keep `max_active` as a setting with default 1; (b) a hard limit of 1, plus a check that the account has nothing else queued; (c) also back off and pause after rejections. Riley asked for (b) + (c).
- **Design** (`download/downloader.py`, state in the manifest):
  - **At most one job queued or running per account, in any dataset.** `Downloader` refuses `max_active` above 1, and changing that needs Riley's OK. Before each submission, our own job is counted from its status, and `active_jobs()` (the CDS job list, status accepted or running) must also be empty. That catches a job left over from a crash, a submission that timed out after the CDS took it, or another process. If either can't be read, nothing is submitted.
  - **Pipelined:** a step polls first, submits the next request as soon as the previous job has finished at the CDS, and only then downloads the finished result. The CDS queue still holds one job.
  - **Rejections:** any job the CDS rejected or failed, and any submit error, is a rejection. Both queue-limit wordings (2026-09: "…is temporarily limited"; 2026-10: "Maximum number queued requests for this dataset has been reached") send the request back to planned without counting as a failure. Other rejections and submit errors fail the request, so it shows in `astro status` and its attempts count; `retry-failed` replans it, but the backoff and the pause still apply.
  - **Backoff:** after a rejection, nothing is submitted for 60 min, doubling with each rejection in the last 24 h. With the pause at 3, that is 60 then 120 min. The 4 h cap only matters if the pause threshold is ever raised.
  - **Pause:** 3 rejections within 24 h pause all submissions until a person runs `astro cds-resume --reason …`. Rejections before the resume no longer count. The notify watcher sends a high-priority alert once, saying what to check and how to resume, and `astro status` shows the pause.
  - **Lost jobs (D34):** a request whose job the CDS loses (HTTP 404, deleted, expired) is submitted again at most twice, then fails. After `retry-failed`, each further loss fails it at once, so the total is bounded.
  - **Can't be bypassed:** the rejections and the pause are rows in the manifest (`cds_rejections`, `cds_control`), so they survive restarts. `run_boxes.sh` no longer passes `MAX_ACTIVE`. `retry-failed` only moves requests to planned. `astro download` submits nothing and returns while backing off or paused. The smoke test runs one at a time too.
- **Counting failed jobs:** a job that failed in processing (not only "rejected") also counts. That is conservative: it costs an hour's pause now and then, against an account that is our only route to ERA5.
- **Tests (`tests/test_cds_gate.py`, fake backend):** one job in flight under random status sequences, poll errors and clock steps (hypothesis; it fails if the gate is removed); both wordings; nothing submitted during a backoff, even after `retry-failed`; the doubling; a stray job at the CDS blocks submission; an unreadable job list blocks submission; a submit error counts; 3 in 24 h pause and alert, and the pause holds until resumed; rejections older than 24 h don't count; lost-job resubmission is bounded; the next job goes in before the finished one is downloaded.
- **Who:** Riley (the rules); agent (the design).
- **Known limits, accepted:**
  - If a submission times out after the CDS has taken it, that job is orphaned: we have no id for it. The job-list check still blocks any parallel submission, so the cost is only that the CDS does that request twice.
  - A request the CDS keeps rejecting for its own reasons trips the pause instead of letting the queue move on. That is wanted: repeated invalid requests are what gets accounts disabled.
- **Review (2026-10-30):** Copilot didn't take the review request on PR #4. The API accepted it, but no request was recorded (on PR #3 it was), so an independent code review was run in its place. It had 10 findings and 8 were fixed: submit errors now fail the request (visible, counted); poll-time rejections count in the run summary; the stall alert is suppressed while paused; `--max-active` accepts only 1; a rejection in the same second as a resume counts; the backoff text matches the code; the lost-job count is commented; one shared test clock. ## 2026-11-06 — Cloud planning session: the F1 verdict

### D48. F1 verdict and model agreement: the exact rules (map #20, ticket #22)
- **Evidence:**
  - Prototype rules: `tonight()` in `web/prototype-forecast-views/core.js` (branch `prototype/forecast-views`) counts dark hours, falling back to Sun below −12°, then below the horizon. An hour is "mostly clear" when `count.clear * 2 > n` over the models that cover the place. Its seeing figure is a median of per-hour cross-model medians.
  - Value timing (`docs/research/forecast-sources.md`): GFS publishes total and low/mid/high cloud both instantaneous and as 6-hour averages. ICON-EU, MEPS and IFS values are instantaneous. IFS open data is 3-hourly (steps 0–144 h every 3 h).
  - Latency after run time: ICON-EU +2.7–3.0 h, MEPS +2.3–4.1 h, GFS +3.6 h, IFS +7.6 h (0.25°). So just before its next run lands, an IFS run is normally up to ~14 h old.
  - Seeing ∝ J^(3/5) is monotonic in J, so the median of an odd number of seeing values equals the seeing of the median J.
- **Choice (Riley, 2026-11-06):**
  1. **Hour:** a forecast model's instantaneous value at hh:00 UTC stands for hh−0:30 to hh+0:30. The hour's Sun class is the Sun's altitude at hh:00. GFS uses its instantaneous cloud fields, never the 6-hour averages.
  2. **Counted hours:** the dark hours (Sun below −18°) of Tonight. Only when Tonight has **zero** dark hours, fall back to hours with the Sun below −12°, then below the horizon (−0.833°). The verdict names the basis. A short dark time (even 1 hour) stays the basis.
  3. **Past hours:** the verdict counts from the current hour to the end of Tonight. The current hour is the one containing now (a step at hh:00 counts until hh:30). Past hours are greyed in the table and not counted.
  4. **Model agreement:** per hour, over the global families (GFS, IFS, ICON; ICON-EU in the F1 box) that have a value for that hour:
     - **mostly clear** when more than half of them put it in the clear class, with at least 2 families;
     - fewer than 2 families: **incomplete**, counted as neither clear nor not clear;
     - each hour also gets a majority class (clear, some cloud or cloudy), or **split** when no class has a strict majority;
     - the table shows count and denominator ("2/2 clear", "2/3 clear");
     - nothing is carried forward or filled: IFS's in-between hours stay blank (D44).
  5. **Runs:** each family uses its latest complete, verified run, and the page shows each run's time and age. A run more than **24 h** past its run time is **stale**: shown, but not counted. A partial run counts only for its verified steps; its missing steps are missing hours under item 4.
  6. **Cloud classes:** keep D43's placeholders (in config): clear T ≤ 10%, some cloud 10% < T ≤ 50%, cloudy T > 50% of total cloud, classified on the **unrounded** value. Revisit with evidence from the Paranal comparison and Kongsberg nights.
  7. **Seeing in the verdict:** one value per counting global family, its median O&S free-atmosphere seeing (D47 headline) over the counted hours, shown as a range ("0.5–0.8″, O&S, free atmosphere, 3 models", "uncalibrated"). The median is taken on J and converted to seeing (for an even count, the mean of the two middle Js). A family with no seeing for any counted hour drops out of the range. If none has seeing: "Seeing: no model has it tonight".
  8. **Template** (wording final with the UI, D44 item 9; the rules are fixed here):
     - **headline:** "x of n dark hours look clear on most models". It says "left" once Tonight has started, names the fallback basis when used ("night hours (Sun below −12°)", "(Sun down)"), and adds "(k hours incomplete)" when there are any;
     - **strip:** consecutive counted hours merged into chips (Clear, Some cloud, Cloudy, Split, Incomplete), in local time;
     - **meta line:** the seeing range with "uncalibrated", the basis, Moon rise, set and phase, and each run with its age, stale runs marked "stale, not counted".
  9. **MEPS:** a separate, visibly secondary line under the headline, "MEPS (regional, not counted): x of n clear", using the same counted hours and the clear rule on MEPS alone. It is not in the strip, the counts or the globe (D45 item 3).
  10. **Nothing to count:**
      - counted hours over before sunrise: "Dark time ended at hh:mm"; the table stays, and Tonight still changes at sunrise (glossary unchanged);
      - every remaining counted hour incomplete: "Not enough models for a verdict: …", naming each family's state (stale, missing), with no counts.
  11. **Landing map (B):**
      - clear layer: the headline count (mostly clear counted hours left tonight), computed by exactly these rules; hatched where there are no counted hours, shaded differently where all are incomplete;
      - seeing layer: a model picker (default GFS, the most levels) showing that family's median per item 7;
      - dark-hours-left layer.
  12. **Glossary:** Counted hours, Mostly clear, Incomplete hour, Stale run and Verdict added to `CONTEXT.md`.
- **Testability:** each item is meant to be checked against a hand-made night: given Sun altitudes, per-family total cloud and J per hour, and run times, the expected counts, chips, range and texts follow uniquely.

### D49. Fog and low cloud in the forecast, and the forecast is a general tool (map #20, research ticket #31)
- **Context:** Riley saw Yr forecast a clear night while meteoblue showed nearly 100% low cloud, and meteoblue was right. On another day, a clear Kongsberg had thick fog in the Skollenborg–Darbu valley. Riley asked whether fog can be predicted from terrain and other weather signals with established, verified science, and set the rule: nothing meteorologists can't do.
- **Evidence:** `docs/research/valley-fog.md` (branch `research/valley-fog`; key sources re-checked by the main session).
  - Yr's 2–3-day forecast for Norway is MEPS; meteoblue's Kongsberg model list has no MEPS.
  - MET Norway's verification reports document MEPS under-forecasting low stratus under subsidence inversions (METinfo 20/2026), with IFS "usually" closer in those cases, and missing inland radiation fog at 1 h lead time (METinfo 14/2023).
  - ECMWF FUG §9.4.1: 10 km models "cannot be expected to handle" patchy fog; site skill "can be very low".
  - Established elsewhere, each with limits:
    - the models' own fog and visibility outputs (low site skill);
    - statistical post-processing at stations with long observation records (e.g. NOAA LAMP, "a statistical system", with ceiling and visibility guidance for "over 2000 stations", vlab.noaa.gov/web/mdl/lamp);
    - observation-threshold nowcasts (hours, not tonight);
    - satellite detection of existing fog.

  1. **A general tool, not a Kongsberg predictor.** The forecast track must work the same way for every place on the globe. Better regional models or data are used wherever they exist (D44, D45: finest version of each family, regional-only models as extra rows), accepting that coverage differs between regions. No method, threshold or feature is specific to a town or small region. Kongsberg (and its box) is the test location while building F1, and Riley's own observations there are test data.
  2. **D45 item 3 and D48 unchanged:** the verdict counts total cloud from the global families only. The evidence doesn't favour counting MEPS for low cloud: its documented gap is exactly low stratus and fog.
  3. **Fog signals row:** per forecast model and hour, the model's own fog, visibility and low-cloud outputs, wherever that model provides them, labelled experimental and **not counted** in the verdict or the map's clear layer. Models without a field show it as absent, never filled. For the F1 sources (fields as listed in the research, section 3):
     - MEPS: `fog_area_fraction`, `visibility_in_air`, `low_type_cloud_area_fraction`;
     - ICON-EU: `VIS`, `WW` codes 45/48, `CLCL`;
     - GFS: `VIS`, `LCDC`;
     - IFS open data: `lcc` and the 2 m dewpoint depression.
     - No combined fog score until one has been verified.
  4. **Terrain caveat, computed per place:** wherever a place's real elevation lies below a model's ground (D47 item 1 already finds this), the page says by how much, and that fog or cold air pooling in terrain below the model ground is not forecast by that model. The same rule applies everywhere; nothing is written for one town.
  5. **No terrain-based fog prediction:** unresolved science, so not built.
  6. **Fog log (test data):** Riley logs observed fog and low-cloud nights (date, time, place, what Yr and meteoblue showed, what happened) while F1 is tested. It is used to judge whether any model's fog signals are worth showing more prominently. It is not a product feature.
  7. **Later, as research tickets (F2 or after), each general rather than local:**
     - statistical fog and visibility post-processing wherever station records allow (the established LAMP-style route), using station observations as a new source [ASK];
     - verification of fog signals against satellite fog and low-stratus products (e.g. EUMETSAT NWC SAF; other regions need their own satellites), also a new source [ASK].

## 2026-11-12 — Cloud session: measurement-only CDS requests

### D50. Measurement-only requests: a `measured` state, and their turn by hold/release (ticket #10)
- **Why:** ticket #11 needs the cost and transfer time of one global hour (29 levels × z, t, u, v, cc = 145 fields, ~300 MB) at one CDS job at a time. A global request can't be ingested without a land/night mask (D18), so ingest would refuse it and the watcher would raise a "refused" alert (D33).
- **Options (marking):** a region-name convention only; a `purpose` column on the request. **(After verify):** leave it `verified`, which `run_boxes.sh` and the watcher count as pending forever; or a terminal state. **(Queue turn):** the downloader submits measurement requests first; or no code, using `astro hold` / `astro release`.
- **Choice:**
  - Requests carry `purpose` (`store`, the default, or `measure`). Opening a manifest made by an older version adds the column with `store` for every existing row; nothing else changes.
  - `astro plan-measure` plans one (default the whole globe, the kind's default variables and levels, region `measure-<label>`, default `measure-global`, so keys never mix with stored requests).
  - It downloads under the D39 gate like any request. Verify checks it fully and moves it straight from `downloaded` to the new terminal state **`measured`** in one transition, so it can never sit in `verified` for ingest. Nothing is written under `/data`, and the raw GRIB stays in `/staging` (never deleted automatically, because there is no ingest).
  - The watcher counts `measured` as progress, never as pending work or a refusal.
  - **Queue turn:** no code. With the download loop and the TMT release timer stopped, the CT holds the other planned requests by request id, saves those ids, and afterwards releases only them (`docs/ct_runbook.md` §7).
  - **Identity:** a measurement's `request_hash` also covers its purpose and key, so the same CDS payload can be measured under another label, or next to a stored request, without breaking the manifest's unique hash. Stored requests hash exactly as before.
- **Review (Copilot, PR #32, 3 findings, all real and fixed):** holding while the loop runs could leave a just-submitted job unrecorded (the loop is now stopped first); prefix release could release earlier holds (now by id); measurement hashes could collide (now include purpose and key; tested).
- **Tests:** `tests/test_measure.py`, against the fake CDS backend: the CLI end to end (one submission, `measured`, no store, timings and verification recorded), the watcher (no alert, not pending, counts as progress), the planner (a global hour is 145 fields), and the upgrade of an old manifest.
- **Who:** Riley (the test points and the hold/release route, 2026-11-12); agent (the design).

- **Evidence:**
  - `docs/research/seeing-measurements.md` (branch `research/seeing-measurements`): ESO's DIMM is on a 7.5 m platform, normalised to 500 nm and unit airmass; MASS "also provides a seeing estimate in a free atmosphere (above 1 km)" (https://www.eso.org/sci/facilities/paranal/astroclimate/asm-instruments.html, re-read 2026-11-16); the ESO archive is CC BY 4.0 (D28).
  - Re-tested 2026-11-16: the anonymous CSV queries for `dimm_paranal` and `mass_paranal` returned 2026-11-14 rows. Rows are about 79 s apart (00:00:13, 00:01:32), so about 45 an hour, and MASS free-atmosphere seeing read 0.80, 0.67, 0.51″ in the first 2.5 min. The MASS table has `Free Atmosphere Seeing ["]`, `MASS Turb Altitude [m]` and `MASS-DIMM Cn2 fraction at ground`; ESO's pages do not say how `MASS Turb Altitude` is defined or what it is measured from. ESO's ambient database also has LHATPRO IR sky temperature, PWV and METEO tables (query-forms page, same day); their data were not examined.
  - Engine: `ProfileResult.j_above(h)` cuts J at a height, and `relocated_integral_above` (`physics/groundlayer.py`) applies O&S's relocation to any Cₙ² profile (generalised to any observer height, an earlier choice of ours).
  - O&S 2018 at Paranal (RESEARCH §3.3): free-atmosphere r = 0.64, bias +0.08″, RMSE 0.16″ (137 model levels); total r = 0.30.
  - D44 item 5 (compare each night with ESO's DIMM and MASS, archive it), D47 (observer height, no ground layer, labels), D48 items 1 and 7 (hour = hh−0:30 to hh+0:30; median on J), D51 items 3, 7, 10 and 12 (Paranal box with GFS and IFS, retries, SSD vs `/data`, per-place stores), D52 (page).
- **Choice (Riley, 2026-11-16):**
  1. **Pairs scored.** For each forecast family (GFS, IFS) and each Cₙ² model (O&S, Tatarskii + HMNSP99):
     - **headline:** free-atmosphere seeing (above observer + 1 km) against MASS free-atmosphere seeing;
     - **total seeing against DIMM, in two series:** D47's no-ground-layer series (a lower bound, expected to read low) and the O&S-relocation series;
     - **stored and plotted, not scored:** H̄ against MASS Turb Altitude, and the ground fraction against MASS-DIMM, until ESO's definitions are checked (a CT task on the first data; what it is measured from, and whether it is H̄ as in D47);
     - **cloud is not compared in #26.**
  2. **Relocation series for both Cₙ² models.** Relocation is geometry on J(h); applied to Tatarskii + HMNSP99 it is our extension of O&S's paper and is labelled so.
  3. **Observer height.** D47 as written: the DEM (GLO-30) height at the place, raised to the model ground only where it lies below it (at Paranal it does not). No +7.5 m for the DIMM platform: the levels are hundreds of metres apart and no ground layer is computed. J starts at the observer using `j_above`, with the straddling slab cut in J, never in seeing. Levels wholly below the observer are masked and counted, and the gap to the first level is shown per model. The DEM height minus the published 2635 m is logged, and flagged above 50 m (GLO-30 is a surface model).
  4. **Runs.** Primary score: the latest verified run of each family at that night's local sunset at Paranal (D48's rule: latest verified, stale after 24 h). Secondary: every run, scored by lead time in 6 h bins up to 48 h, as a table of bias, RMSE and r. No run is pooled into the primary statistics.
  5. **Hour match.** One ESO value per hour: the **median** of all samples in [hh−0:30, hh+0:30), kept with the sample count and interquartile range. Hours with fewer than 10 samples are not scored, and are counted and logged. The median needs no conversion (seeing is monotonic in J, so it matches D48 item 7). Nothing is clipped; only missing or non-numeric values are dropped, and they are counted.
  6. **Pairing.** Only **matched hours** are scored: the family has a value and ESO has an hour value. A night's forecast and ESO medians are taken over the same matched hours, and a night needs at least 4 of them. Per night the record lists counted hours, hours with ESO data, matched hours, and the reason for each missing hour (monitor off, <10 samples, IFS off-step, no run, stale run). Nothing is filled or carried forward. The report states that ESO measures only while the monitor is open, so scores are conditional on that.
  7. **Statistics,** per family × Cₙ² model × series, hourly and nightly-median: n, bias (forecast − ESO, ″), RMSE, Pearson r, Spearman ρ, and the RMSE of a persistence baseline (previous night's ESO median, same series). Below 20 scored nights they are printed with "n too small for intervals"; from 20 on, with a bootstrap-by-night 90% interval. The comparison never fits or changes a constant (calibration stays with the historical track; changing one is [ASK]).
  8. **ESO fetch** (left to this ticket by D51). Once a day at about 17:00 UTC (just after local mean solar noon at Paranal, which ends the Night), a step of the existing 15-min tick, not a new timer, fetches the finished night's DIMM and MASS rows, one query each. The same night is fetched again 3 days later, as a second, separate file. Raw CSVs go to `/data/astro/validation/eso-asm/` with fetch time and checksum, written once and never overwritten. Retries as D51 item 7, generic User-Agent, about 4 requests a day. ESO is already approved (D28, D44), so this adds no source.
  9. **Archive.** The morning after, a night is scored from the first fetch and kept on the SSD marked provisional (the page says so). After the re-fetch, the final matched table is written once to `/data` (hourly pairs for every family, Cₙ² model and series; run IDs; ESO file checksums; commit and config hash) and replaces the provisional one. A night never changes after that; a later change of method is a new, separately named version. Pairs are stored, so any later rule can be recomputed.
  10. **Where it shows.** A "Paranal check" panel on the Paranal place: last night's hourly pairs (ours next to MASS and DIMM, with ESO's IQR), and the statistics over the last 30 scored nights with n, coverage, the D47 labels ("uncalibrated", Cₙ² model, level count, observer height) and ESO's credit line. Plus a generated weekly Markdown report (all-time and last-4-week tables, the lead-time table, missing-hour reasons) written to `/data` and linked from the panel.
  11. **What F1's approval needs from this.**
      - 28 consecutive nights of unattended running: no manual step, the page fresh, every failure alerted (D51, D52);
      - at least 20 scored nights for each of GFS and IFS;
      - the 7-day measured-size report (D51 item 11);
      - a hand-made `reports/f1.md` with the statistics above, coverage and missing-hour reasons, alerts raised, and O&S's numbers as context only.
      - **No pass mark on r or RMSE:** F1 seeing is uncalibrated and there is no evidence to set one. A statistic that looks wrong (a negative free-atmosphere correlation, a bias of several tenths of an arcsecond, hours lost systematically) must be explained before approval. These numbers become the baseline a calibrated forecast must beat in F3.
- **Not decided:** how ESO defines `MASS Turb Altitude` (item 1); whether LHATPRO IR sky temperature can serve as a cloud proxy (a later research ticket, which D48 item 6's revisit of the cloud classes can use).

  1. **Own manifest tables.** `ts_requests`, `ts_events` and `ts_stores` in the same manifest (created on every open, like the forecast tables), not rows in `requests`. States: planned → submitted → verified → stored, any → failed (`--retry-failed` → planned, up to 5 attempts), and cancelled (`--replan`).
  2. **Own slot, both ways. This amends D39's "at most one job queued or running per account, in any dataset"** for one product: `DatastoresBackend.active_jobs()` (the D39 gate's check) now leaves out jobs whose `processID` is `reanalysis-era5-single-levels-timeseries`, the only product D29 measured in its own slot (the pressure-level time-series product still counts: its slot is untested). A lost job (D34) is submitted again at most twice (`MAX_LOST_RESUBMITS`), then fails.

If the CDS refuses or truncates it, the chunk fails (rejection or verification) and `astro fetch-sp --replan --chunk-years 1` replaces the site's unfinished chunks (it refuses while a chunk is at the CDS, and never touches a stored site). A different chunk size without `--replan` is refused, so chunks never overlap.

### D74. Tonight: how the verdict rules are built, and Riley's answers on the MEPS line and the end of dark time (ticket #53)
- **Context:** ticket #53 builds D48 as one pure function, `tonight()`, plus `moon_track` (F1 spec #47, Module 5, Testing seam 2), and asks for its non-trivial choices to be logged. It says to ask Riley where a D48 rule is ambiguous in a test case rather than choose.

- **Choices (items 1–9: agent, provisional; item 10: Riley; nothing here changes a decided rule):**
  1. **Layout and interface.** `forecast/tonight/` holds `shapes` (`HourTable`, `SunTrack`, their parts), `rules` (`tonight()`), `sun` (`sun_track`) and `moon` (`moon_track`). `tonight(hours, sun, now, *, cloud_classes, stale_after_h)` takes the two settings values as arguments, so it stays pure and reads no file.
  2. **Stale is decided inside `tonight()`,** from each run's time and `now` (D48 item 5 in one place). The `HourTable` keeps a stale run's values, so the table can still show them; its missing reasons are only `off_step`, `no_run` and `partial`, as in the place schema.
  3. **Dark hours and the fallback.** An hour is dark when the Sun's altitude at hh:00 is below −18° (D48 item 1). The fallback applies only when the whole Night has no such hour (D48 item 2: "zero dark hours"), so the basis doesn't change as the night goes on; the glossary's "no dark time at all" is read through D48. "Sun down" is the geometric altitude below −0.833°.
  4. **Started and the current hour.** Tonight has started from local mean solar noon (the Night's start in `CONTEXT.md`), so the headline says "left" from then on. Before that `current_hour` is null and no hour is past. In the half hour after noon the current hour can be the hh:00 just before Tonight's first row (11:00 UTC at Kongsberg between 11:21 and 11:30); every row then counts.
  5. **Majority and chips.** Every hour with at least one family gets a majority class (for an incomplete hour, its one family's class, which the table may show); an hour with none has none. In the strip an incomplete hour is always an "Incomplete" chip. A chip's `start` and `end` are its first and last hours' hh:00 (inclusive); only consecutive hours merge.
  6. **Seeing range.** Incomplete hours are counted hours, so their J counts in each family's median; stale families are out. Seeing comes from `physics.optics.seeing_arcsec` (500 nm, zenith, the exact 5.307 form, D47 item 6). A J that isn't finite and positive is refused, never dropped.
  7. **Each family's state for "Not enough models".** Global families only, keyed by family: `stale` (stale run), `missing` (no run), `ok` (a value in at least one counted hour left), else `partial` if its run lacks any of those steps, else `off_step` (IFS has no step at those hours). `off_step` is new in the schema's list.

  9. **Schema amendments (`f1-place/1`, as D71 item 9 allows):** `tonight.meps` gains `missing_hours` and `stale` (item 10); `nothing_to_count.families` gains `off_step` (item 7). The place fixture is updated to match.
  10. **Two cases D48 doesn't settle, asked on ticket #53; Riley chose the agent's recommendation for both (2026-11-26):**
      - **The MEPS line when MEPS lacks hours or its run is stale: option B.** n stays Tonight's counted hours, and the line also reports how many of them MEPS has no value for ("x of n clear (k hours missing)"). A MEPS run more than 24 h old has all its hours counted as missing, and the line says it is out of date. Rejected: A, the gaps simply not clear, with an old run used as is; C, n counting only the hours MEPS has.
      - **The time in "Dark time ended at hh:mm": option A.** It is the time the last counted hour stopped counting (its hh:00 + 30 min, D48 item 3), which is the moment the message appears. Rejected: B, the real end of darkness to the minute, which can lie up to half an hour ahead of the message; C, the last counted hour's hh:00.

### D75. Saved places' GLO-30 heights: which posting, which tile, how it's checked, where it's written; Paranal as a saved place (ticket #54)
- **Context:** ticket #54 (F1 spec #47 Module 6, user story 29; D47 item 1, D54 item 3, D60 item 1) builds `astro forecast place-height <id>` and asks for its non-trivial choices to be logged.
- **Evidence (all checked 2026-11-26 from this cloud session):**
  - Two real tiles were downloaded from the public bucket (`Copernicus_DSM_COG_10_N59_00_E009_00_DEM`, 30 671 507 bytes; `..._S25_00_W071_00_DEM`, 21 928 523 bytes). The tiles' metadata XML says cell geometry "point" and counts 3601 × 2401 valid postings for N59, while the GeoTIFF holds 3600 × 2400: the south row and east column are left out, as they are row 0 / column 0 of the neighbouring tiles. N59 has 2400 columns (1.5″, RESEARCH §7's ×1.5 band); S25 has 3600.
  - N59's column spacing is stored as 0.00041666666666666664, one rounding step below 1/2400.
  - Our reader, run over every block of both tiles, gives arrays identical to GDAL 3.12.2 (rasterio 1.5.2, installed in a throwaway environment outside the project), and picks the same postings as GDAL's `index()` for both places.
  - Each tile's S3 `ETag` equals the MD5 of the downloaded bytes. AWS's S3 API reference (https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html, "ETag") says objects created by a single PUT, POST or Copy, plaintext or SSE-S3, "have ETags that are an MD5 digest of their object data", and multipart uploads don't. The bucket publishes no other checksum (a listing of the N59 folder shows the DEM, auxiliary masks, previews, metadata XML and the EULA). S3 answered `If-Match` with that ETag with 206, and with another value 412.
  - Paranal: ESO's "VLTI Station Position Technical Data" (https://www.eso.org/observing/etc/doc/viscalc/vltistations.html) gives "The physical location of the array centre": longitude −70.40479659°, latitude −24.62794830°, no datum stated. ESO's site page (https://www.eso.org/sci/facilities/paranal/astroclimate/site.html) gives only 24°40′ S, 70°25′ W for the site and per-telescope positions (UT1 −24°37′39.44″, −70°24′18.27″, …; the four UTs lie 46–131 m from the array centre, VST 199 m, VISTA 1.5 km away on its own summit), and an altitude of 2635.43 m. - **Choices (agent, within the approved spec):**
  1. **The height is the value at the posting nearest the place**, read from the tile itself, never interpolated; the posting's row, column and position are written with it. GLO-30 is pixel-is-point, so this is also the pixel whose area (in GDAL's view) holds the place. A place exactly halfway between postings takes the one to its south-west (the F1 spec's map-grid tie rule), decided in exact arithmetic on the decimal coordinates written in the settings file.
  2. **Which tile:** the one named by the floor of the place's latitude and longitude; if the nearest posting falls on its south or east edge (row 3600 or the last column + 1), that posting is row 0 / column 0 of the tile below or to the east, which is then fetched instead. The rule reads the spacing from each tile rather than from a table, so it holds in every latitude band, including 59.7° N's 1.5″ columns.
  3. **The reader is our own** (about 150 lines, numpy and zlib), not a new dependency: rasterio/GDAL aren't in the environment and adding them changes the lockfile. It reads only the layout above and refuses anything else by name (another registration, compression, predictor, data type, a tiepoint off the tile corner, a grid not spanning exactly 1°, no-data −32767 or NaN), so a format change fails instead of shifting a height by a pixel. Header numbers count as the simple fraction they stand for within a relative 1e-12, which accepts N59's stored spacing.
  4. **Checksum:** each tile is checked against its S3 ETag as an MD5 before it is read, and fetched with `If-Match` so a change between the HEAD and the GET is refused. A tile whose ETag isn't a plain MD5 is refused, not trusted; an SSE-KMS object (32 hex digits but not an MD5) would fail the comparison, loudly. The SHA-256 of the tile read is what goes into the settings file; the tile itself is downloaded to `/staging/tmp` and deleted, never committed.
  5. **Where it's written:** the command rewrites only that place's `height` entry in `configs/forecast.yaml`, keeping comments and every other value: it re-reads the new text and checks it equals the old data with only that entry changed, validates it as settings, and replaces the file atomically. The entry holds `metres` (the float32 value's shortest decimal), `source: glo30`, `tile`, `sha256`, `posting` and the Copernicus DEM `attribution` from RESEARCH §7 (the settings refuse any other wording). A failed lookup writes nothing.
  6. **The bucket URL and the 50 m flag are settings** (`place_heights.dem`, `place_heights.flag_published_difference_m`), and each place has `published_height_m` (null if none). The difference from a published height is logged for any place that has one, and flagged as a warning above 50 m (D54 item 3), rather than special-casing Paranal.
  7. **The tick's check** is `forecast.places.require_looked_up_heights(settings)`: it raises naming every place whose height is missing or hand-entered, with the command that fixes each. The tick (F1-2) calls it.
  8. **Paranal is a saved place** at ESO's VLTI array centre (the ticket adds it; D71 item 3 had left it to the Paranal check ticket). It is ESO's own decimal position, on the VLT platform among the telescopes, and given to the centimetre, where the repo's two-decimal value could be several hundred metres off on a steep summit. Time zone America/Santiago; area `paranal` (D71's 1° box, which holds it).

Each step is tried at most 5 times **in all** (any host, any tick), never sooner than 1 min after its last try; every try is a row in the new `forecast_step_tries` table. Each tick asks the adapter, in one `fetch`, for the steps that are ready; a step's try asks each of its files at most once, so no file is ever asked more than 5 times. Retrying inside one tick (5 tries a minute apart) would hold a tick for minutes per file and lose a step for good after a 5-minute blip.
  2. **The host check and the fallback.** Each tick starts with the adapter's cheap newest-run check on the **main** host. An answer (even "nothing new") means the main host works; no answer starts its failure clock (`forecast_hosts.main_failing_since`, the first unanswered check). Once that has lasted 1 h and the model has a fallback host, the model switches to it, logged once, and asks it instead. A host that doesn't answer the check gets no fetch that tick, so an outage costs no tries. A main host that answers the check but fails the files themselves isn't "failed" in this sense: those steps use up their tries.
  3. **The return rule:** the model goes back to the main host at the first tick whose main-host check answers, logged. Any step still missing is then fetched from the main host. Runs fetched from both hosts read as one (the GFS files are written under the same names from either host).
  4. **Partial runs count at once.** Every tick that fetched new steps reads, verifies and stores the run from all its fetched files, so the page has its verified steps straight away; missing steps are listed per step ("not tried yet", "try 2 of 5 failed: …", "5 tries failed; last: …"). Raw files stay on `/staging` while any step has tries left and go once the run is **final** (every step fetched or out of tries), after the stored values are read back. `partial` therefore means "stored for its verified steps"; it is final once nothing is left to try.
  5. **Abandoned:** a run still fetching is given up when a newer run of the same model and area is `processed`, or 4 h before its online window ends (ICON-EU 20 h after the run). It keeps the steps it stored, which still count when it is the newest run (the window case); an abandoned run counts as usable only if it stored something. Each missing step's reason is prefixed "abandoned (why): …", its raw files go, and nothing more is fetched for it.
  6. **Failed runs** (a format change or failed verification) are not fetched again: the fix is a ticket (D51 item 8). Their raw files are kept for that fix until the run would have been abandoned (a newer run complete, or the window), then deleted; the run stays `failed` with its error. D51 item 5's "once it is retried" has no case here, since nothing retries a failed run automatically. If a run fails after an earlier tick stored some of its steps, that stored file (on the SSD, never `/data`) is removed so the page shows the model as missing, not a failed run.
  7. **Late:** the newest run that should be out by now (run time + publish delay) is late from delay + 3 h until it is seen. Each tick logs it as a warning and lists it in the tick report; nothing is written to the manifest and nothing alerts.
  8. **GFS from AWS (`GfsAdapter.on_fallback()`):** one GET of a file's `.idx`, then one ranged GET per run of adjacent needed messages, instantaneous only (`anl` at step 0, `N hour fcst` after); a needed message missing, listed twice or for another run is `FormatMismatch`. The bytes are written under NOMADS's file name for that step. `read` cuts a global 0.25° field to the area's points as it decodes (west → east, wrapping at 0°); any other grid must still be the area's own. No pacing: the settings give the bucket no rate limit.
  9. **IFS (`IfsAdapter.on_fallback()`):** the same adapter on the AWS mirror (paths without `/forecasts`, D77). `fetch` now accepts any steps (D77 item 4's check that `fetch` includes step 0 is dropped, since the tick asks only for missing steps); `read` still refuses a run without step 0.
  10. **Deletion is narrow:** only files recorded for the run in `forecast_files` **and** inside its own raw folder `/staging/forecast/<model>/<run>/<area>/` are deleted; any other path is logged and left. Nothing else under `/staging` is touched.
  11. **Records:** two new tables, created like the others on every open (an old manifest gains them and nothing else): `forecast_step_tries` (run, step, host, time, error) and `forecast_hosts` (model, current host, main failing since, switched at). `attempts` counts the ticks that fetched for a run. A file fetched again (a retried step) is recorded again; the latest row for a path is the one read.
  12. **`RatePacer`** moves from `sources.gfs` to `forecast.http`, beside the client, for any adapter whose host states a rate limit (F1-8's review).
- **Consequences worth knowing:** a MEPS retry re-asks its four small metadata requests (D78 item 1) with the missing steps. A host that dies in the middle of a fetch costs each remaining step of that fetch one try. Tests run the window rule on GFS samples under ICON-EU's settings (24 h window, no fallback), since the ICON-EU adapter (F1-6) isn't on `dev` yet.
- **Who:** agent (provisional), within the approved F1 spec.

## 2026-11-27 — Cloud session: per-place daily stores on the NAS (roadmap F1-10, ticket #59)

### D80. Per-place daily stores: when a day is final, the store layout, the write-once rule, the NAS timeout, and the SSD copy (ticket #59)
- **Context:** ticket #59 (F1 spec #47, Module 6; D45 item 5, D51 item 12) moves each saved place's stored runs of a UTC day from the SSD to one Zarr v3 store on `/data` once the day's runs are final, never touched again, with a timeout on the NAS, and asks for its non-trivial choices to be logged.
- **Evidence:** AGENTS.md (the NAS hangs rather than failing; atomic writes; `/data` only grows; Zarr v3, few files on NFS); D51 items 5, 7, 10 and 12; D79's run states and rules; a full synthetic day measured in this session (below).
- **Choices (agent, provisional; no decided rule changes):**
  1. **When a day is final.** Every run the place's area expects that UTC day (each area model at each of its `runs_utc` hours: 16 at Kongsberg, 8 at Paranal) is `processed`, `abandoned`, `failed`, or `partial` with no step left to try (D79 item 4). A run with **no manifest row** counts as final, and is named in the store as "never seen", once it can no longer appear: a newer run of the model has been seen (the tick only ever fetches each model's newest published run, D72 item 7), or the source's online window less the abandon margin has passed (D79 item 5). Without this rule a day the service missed (the CT was down, ICON-EU's 1-day window) would never be written. `failed` counts as final: it is never fetched again (D79 item 6) and its stored values are already gone.
  2. **Which days:** the UTC days with run files on the SSD (`/staging/forecast/products/places/<place>/<day>/`). A day whose runs all failed has no folder and gets no store; the manifest keeps those runs.
  3. **What the store holds:** every stored run's document, losslessly, so `hours_for` reads `/data` exactly as it reads the SSD. Per model, one group with two float64 arrays: `step_values` (run × step × field: every number of every stored step, `stored` = 1 where the run has the step; text such as the cloud class held as codes, fog signals the model lacks as NaN with the run's list of absent signals, null as NaN) and `run_values` (run × field: run id, run time, observer height, raise, model ground, place height, level count). The rest of each run's document (metadata, missing steps with reasons, QC counts, the run's provenance) sits in the group's attributes. The root attributes hold the writer's provenance (commit, config hash, software, the manifest run ids in the store), each expected run with no stored values and why, each model's credit line and the Copernicus DEM credit for the place height, and a SHA-256 of the run documents as canonical JSON. Two arrays per model keep a store to ~21 files on NFS; each array is one Blosc-zstd chunk.
  4. **Written once.** Into a temp folder beside the store, read back and compared with the SSD documents, fsynced, then renamed into place (a rename that fails if the store appeared meanwhile). Once written (or found), the day is recorded in a new manifest table `forecast_place_days` (place, day, outcome, path, bytes, content hash), created like the other forecast tables on every open; a recorded day is never looked at again, so later ticks don't touch `/data` for it. A store already there with **the same** runs is recorded as `exists` and left untouched; one with **other** runs is refused, logged as an error, recorded as `refused` (so it is logged once, not every tick) and never overwritten. The only thing ever removed on `/data` is the write's own temp folder when that write fails before its rename: it was never content. A temp folder left by a write whose process died (a hang) is never deleted: each later write beside it logs it as a warning.
  5. **The NAS timeout:** every call to `/data` (write, read) runs in a daemon thread and is given up after `place_stores.nas_timeout_s` (60 s); the call is left to finish or not on its own. While one call is still hanging, later calls in the same process fail at once instead of piling up, and the tick stops finalising for that tick. Nothing is recorded, so the next tick (a new process) tries again; a write that finally completes is found next time as `exists`. Finalising runs after publishing (spec order, step 6), so a hang never holds the page back. Threads rather than child processes because NFS hard-mount waits are killable, so the tick process still exits, and the fake slow NAS in the tests stays in-process.
  6. **The SSD copy:** a written day stays on the SSD for `place_stores.ssd_keep_days` (2) more days, then its run files are removed, oldest day first, stopping at the first day not yet written. So every day kept only on `/data` is older than every day still on the SSD, and Tonight is normally read from local disk.
  7. **`hours_for` reads both.** Each model's newest stored run **that can reach the given hours** (run time no earlier than the first hour less the model's last step), from the SSD; only for a model with no such run there does it read the days in that window that are no longer on the SSD from `/data` (under the timeout; a hang leaves that model without a run this time, logged). That read comes before publishing, so a hung NAS can delay one publish by up to the timeout, once per tick; with the 2-day SSD copy it happens only for a model with no run for about two days. A run that can't reach any hour of Tonight is no longer listed: it gave every hour "no run" before, and `HourTable` can't hold a run with every hour "no run" anyway. This bound keeps `/data` reads to a few days at most. `hours_for` still returns the store's `PlaceHours`; F1-14 builds the `HourTable` from it.
  8. **Settings:** a new `place_stores` section in `configs/forecast.yaml` (`nas_timeout_s: 60`, `ssd_keep_days: 2`); the `/data` root is `ASTRO_DATA_ROOT` + `/forecast/places`, like the other `Paths`.
- **Measured (one full synthetic day, random values, so an upper bound):** 193 KB per day at Kongsberg (16 runs; 97 KB of compressed arrays, 89 KB of attributes, mostly QC counts and run metadata) and 85 KB at Paranal (8 runs): about 70 MB and 31 MB a year. D45's estimate was ~46 KB per place per day; the 7-day size report replaces both with real numbers.

## 2026-11-27 — Cloud session: forecast status and the measured-size report (roadmap F1-11, ticket #60)

### D81. `astro forecast status` and `astro forecast size-report`: read only, what they show, and how missing values look (ticket #60)
- **Context:** ticket #60 (F1 spec #47, CLI; user story 49; D51 item 11, D45 item 5) asks for two read-only commands over the forecast's manifest tables and store folders, the second writing a Markdown report that sets measured sizes against D45's and D51's estimates. The real report runs on the CT after 7 days (F1-22).
- **Choices (agent, provisional; no decided rule changes):**
  1. **Read only by construction.** Both commands open the manifest with SQLite's `mode=ro` (`forecast.report.ReadOnlyManifest`), not through `Manifest`, which creates tables and upgrades columns on every open. Any write raises; a missing manifest is an error and is never created. The folders are only listed and measured (`lstat`, links not followed). The only file written is the report, atomically, in the repo's `reports/` (or `--out`). Its header carries the commit, the astroseeing version and the forecast settings hash, and each run row its `forecast_runs.id` (provenance).
  2. **Status:** for each model and area in the settings (then any other the manifest holds), the newest runs (4 by default, `--runs`) with state, age from run time, and steps verified as `ok/expected`; and the newest *usable* run (as the page picks it: processed, partial, or abandoned with stored values) with its age and whether it is stale (over the settings' `stale_after_h`, 24 h). Older runs are naturally over 24 h, so staleness is said once per model, of the run the page would use.
  3. **Last tick:** `last_at` of the tick's one-row heartbeat (`forecast_heartbeat`, D82), read with F1-12's own `forecast.alerts.read_heartbeat` on the read-only connection (it only reads). A manifest with no finished tick, or older than the heartbeat, shows "not recorded".
  4. **Range:** runs whose run time is in `[start, end)`; by default the 7 days before now. A day store counts in the range when its 00 UTC does.
  5. **Missing is never zero.** A value the manifest doesn't hold (bytes before a fetch, processing seconds of a failed run, steps of a run never verified) is printed `missing`. Every total says over how many runs it is taken ("20000000 (1 of 2 runs)"); steps verified are totalled over the runs that have a value. A configured model with no runs, an absent store folder and an absent products folder all show as `missing`.
  6. **Exactness:** bytes are exact integers, seconds are rounded to the millisecond, the publishing delay (first seen minus run time) to 0.01 h. Human sizes (decimal KB/MB/GB, as the estimates are written) appear only in the estimates table.
  7. **The estimates compared:** ICON-EU ~4.4 GB per 48 h run (D51 item 3); D51's evidence per 0–36 h run (GFS ~30 MB, ICON-EU ~3.3 GB, MEPS ~1 GB, itself an estimate, IFS ~0.46 GB), against each model's median raw bytes per run in the default place's area, noting our runs are 0–48 h and the bytes are as downloaded (ICON-EU's files are bz2-compressed); ~46 KB per place per day (D45 item 5) against the mean day-store size in the range; F1 grids under 1 GB (D45 item 5) against everything under `/staging/forecast/products` now.
  8. **Which day stores, and where:** the days the manifest records as settled in `forecast_place_days` (D80), each measured on disk at its recorded path under `ForecastPaths.place_days`. Days recorded as stored but absent on disk, refused days, and entries in a place's folder the manifest doesn't record (a temp folder) are each listed by name under the table, never silently skipped or counted as zero.
- **Testing:** the end-to-end tick world runs a fake week of GFS runs (processed, partial, failed, a late sighting, one seen but not fetched for want of disk), with fake day stores on `/data`; expected numbers come from the sample files' sizes and the fake clock. Download and processing seconds are wall-clock in the tick, so for those the test checks the report against the manifest, not hand-made totals; a hand-filled manifest checks them exactly.

## 2026-11-27 — Cloud session: forecast alerts and the daily health line (roadmap F1-12, ticket #61)

### D82. Forecast alerts: what each condition means exactly, where their state lives, and how the watcher sees the tick (ticket #61)
- **Context:** ticket #61 (F1 spec #47, Module 8; D51 item 9, D52 item 10) asks for five high-priority alerts, each sent once when its condition starts and once when it clears, plus one forecast line in the 06:00 daily message. D51 item 6 says the download watcher never reads the forecast tables, while the ticket has the watcher check the tick's heartbeat and the daily message is the watcher's.
- **Choices (agent, provisional; no decided rule changes):**
  1. **State in the manifest.** The active forecast alerts live in a new `forecast_alerts` table (key, title, start time, message), so a restart or a missed tick repeats nothing. A condition alerts when it is active and has no row, and clears when it is inactive and has a row. A start goes out at high priority, a clear at default priority. A send that fails is logged and not recorded, so the next tick sends it again. Like the other forecast tables, it is created on every open: an old manifest gains it and nothing else changes.
  2. **Stale model:** per worked model and area (an area with a saved place, a model with an adapter), active when its newest **complete** (`processed`) run is more than `alerts.no_complete_run_h` (24 h) old. The clock starts no earlier than the forecast's first finished tick, so a new install is not reported stale before it could have fetched anything. A partial or abandoned run does not stop it ("complete", as the ticket and D51 item 9 say).
  3. **Run failed:** per worked model and area, active while the newest `failed` run is newer than the newest run with stored values (`processed`, `partial`, or `abandoned` with values). Every failed run counts, not only a failed verification: a format mismatch at fetch or read, an unreadable file, or every step out of tries all leave the model missing and are never retried (D79 item 6). The message names the model, run, area and the run's error (its first 300 characters), which holds the difference. It clears when a newer run of that model and area stores values; a second failure while it is active sends nothing new.
  4. **Disk low:** measured once at the start of every tick on `/staging/forecast` (before any fetch), active below `alerts.staging_min_free_gb` (20 GB). The runs keep their own per-run skip and log (D79).
  5. **Page not served:** after publishing (the spec's step 9), the tick GETs `alerts.served_latest_url` (new setting, default `http://127.0.0.1:8350/data/latest.json`, where F1-13's nginx is expected to serve `products/`; the page's own `../data/` meta points there) with a 10 s timeout, and compares the bytes with the `latest.json` on disk. Active when the request fails or the bytes differ; the message names the URL and the error, or both set IDs. The tick is given its HTTP client (`http`); without one (the existing tests) the check is skipped.
  6. **No tick for 1 h: a heartbeat.** Every tick that finishes writes one row in a new `forecast_heartbeat` table, last: first tick time, last tick time, the threshold (`alerts.no_tick_h`, so the watcher needs no forecast settings) and a health summary per worked model and area (name, `processed` runs whose last update falls in the 24 h before the tick, newest complete run time). A refused tick (no looked-up height), a locked one, or one that crashes writes nothing, so all of them count as "no tick". `notify.check_once` alerts once when the heartbeat is at least the threshold old and clears once a newer heartbeat arrives (its state is a new `WatchState.tick_alerted_at`, in the watcher's own state file). Before the forecast's first tick there is no heartbeat and no alert.
  7. **The watcher reads only the heartbeat** of the forecast's records, never `forecast_runs`; D51 item 6's separation holds for everything else. The daily line is built from the heartbeat's summary: `Forecast, runs completed in the last 24 h (as of the hh:mm UTC tick): <area> <model> <n>, newest <yyyy-mm-dd hh>z (<age> h old); …`, ages computed at the watcher's time. It is appended as a second line of the existing daily message, only once a heartbeat exists.
  8. **The notifier:** `astro forecast tick` sends through the same ntfy topic as `astro-notify` (`ntfy_url()`). With no topic configured (or a topic file readable by others) the alerts go to the log only, with a warning, rather than failing the tick.
- **Consequences worth knowing:** a model that is stale and also has a failed newest run sends both alerts. A whole-tick crash shows only as "tick stopped" after 1 h. The served-page alert depends on F1-13 serving `products/` at `/data/`; if it serves them elsewhere, only the setting changes.
- **Who:** agent (provisional), within the approved F1 spec and ticket #61.

### D83. The page's deploy, the web server and the tick timer: how they are built and tested (ticket #62)
- **Context:** ticket #62 (F1 spec #47 Module 11 and Module 8's timer; D51 items 1 and 4, D52 items 5, 7, 8, 9; D32) writes the setup files and `astro web deploy`; installing them is F1-21. Nothing here changes a decided rule.
- **Evidence (checked 2026-11-27 from this cloud session):**
  - conda-forge's nginx 1.31.10 installs with `pixi global install` into any `PIXI_HOME`; its exposed `bin/nginx` runs `sbin/nginx -p <env>` and a later `-p` wins. Run as uid 65534 with an empty environment and no `user` directive, `nginx -t` and the server itself work, writing only its pid, temp and log files. `/root` is mode 700 on this container (Ubuntu's default), so a dynamic user could not run `/root/.pixi/bin/nginx` even without `ProtectHome`.
  - `systemd-analyze verify` (systemd 255) reports unknown keys on stderr with exit status 0, and refuses an `Exec` binary that doesn't exist; `systemd-analyze calendar` gives the timer's next times.
  - nginx sends a weak ETag on a gzip response and still answers its `If-None-Match` with 304; it resolves the `current` symlink per request, so a deploy needs no reload. Nginx Proxy Manager's access lists add `deny all` after the Allow lines (its `backend/templates/_access.conf`), and its UI labels are those in `frontend/src/locale/src/en.json` (both on GitHub, `develop`).
- **Choices (agent, provisional):**
  1. **Deploy (`astroseeing.forecast.deploy`, `astro web deploy [--rollback]`):** the copy of `web/` is read from the commit's git objects (`ls-tree` + `cat-file`), so uncommitted or untracked files never reach the site; anything in `web/` that isn't a plain file (a symlink, a submodule) refuses the deploy. It is written to `site/.tmp-<commit>/`, every file read back against its SHA-256, the checksums kept as `site/<commit>.sha256`, then renamed to `site/<commit>/`. Files are 644 and folders 755 whatever the umask, for nginx's dynamic user. `version.json` (`{"commit": …}`) goes at the copy's root, as the page expects (D73 item 2).
  2. **The switch:** `current` and `previous` are relative symlinks, each replaced by one `rename(2)`, so `current` always exists (tested with a reader resolving it throughout 100 swaps; an unlink-then-link version fails that test thousands of times). A deploy points `previous` at what was live, then `current` at the new commit; deploying the live commit again changes nothing. `--rollback` swaps the two (`current` first), so the same switch goes back and forward. Before a copy goes live again it is checked against its checksums, and a changed copy is refused. One deploy or rollback at a time (`flock`), and each is a line in `site/deploys.jsonl`. Old copies are kept (about 50 kB each today); pruning them is left for later.
  3. **The tick's "at most 2 worker processes, normal priority" in the unit:** the tick is one process (D72 item 12); the unit caps numeric libraries' thread pools at 2 (`OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`) and the service at `CPUQuota=200%`, with `Nice=0` and no scheduling class. `Type=oneshot`, started by the timer at `*:00/15` UTC with `Persistent=true` (a tick still running isn't started twice); `RequiresMountsFor=/data/astro /staging`; output appended to `logs/forecast_tick.log`.
  4. **Tick timeout `TimeoutStartSec=3h`:** a hung NFS mount must not block forever (AGENTS.md), but a whole-box ICON-EU run is thousands of requests (D76 item 6) and the tick resumes where it stopped; the "no tick for 1 h" alert (D51 item 9) reports a stuck tick long before. While a tick runs, the timer starts no other, so a tick stuck in NFS I/O (D80 item 5 leaves a hung call in its thread) holds up the ticks after it until the mount answers or the timeout ends it; the page's "data not updating" banner and that alert show it. A live check for F1-21.
  5. **nginx's home:** installed with `PIXI_HOME=/opt/astro-web/pixi pixi global install "nginx==1.31.10"`, outside `/root`, since `ProtectHome=yes` hides `/root` and a dynamic user can't enter it anyway. Its config is `scripts/nginx/astro-web.conf`, installed as `/etc/astro-web/nginx.conf` (`/home` is hidden too).
  6. **The sandbox:** besides the ticket's `DynamicUser`, `ProtectSystem=strict`, `ProtectHome=yes` and `NoNewPrivileges=yes`, `TemporaryFileSystem=/staging:ro` with `BindReadOnlyPaths=` of the site and products folders hides the rest of `/staging` (the ERA5 GRIB, raw forecast files). Own folders: `RuntimeDirectory=astro-web` (pid and request buffers) and `LogsDirectory=astro-web` (access log); errors go to the journal. The two served folders must exist before it starts, so `install_services.sh` creates them; `RequiresMountsFor=/staging` keeps it from binding an unmounted mountpoint. The site's place is `ForecastPaths.site`, beside the tick's other folders.
  7. **What nginx serves:** the site root is `site/current` (`/` redirects to `/forecast/`); `/data/latest.json` (no-cache, ETag), `/data/sets/` (`public, max-age=31536000, immutable`: a set never changes, D72 item 11) and `/data/sunset/` (no-cache) map onto the products folder, and every other `/data/` path is 404, so the tick's own stores aren't served. Page files and `version.json` are no-cache, so a deploy or rollback shows at the next load. gzip for JSON, JavaScript, CSS and the binary layers (`application/octet-stream` for `.u8`, `.u16`, `.i16`), with `gzip_proxied any` because requests come through NPM; JavaScript as `text/javascript`, which module scripts require; no directory listings, no hidden files, no version in `Server`. It listens on all addresses at port 8350; only NPM is meant to use it, and the tick's "page not being served" check reads `http://127.0.0.1:8350/data/latest.json` (F1-12's `alerts.served_latest_url`, kept as it is; a test ties the two). The ETag is nginx's own (mtime and size): two sets written within one second with the same `latest.json` size would share one, which 15-minute ticks don't do.
  8. **`install_services.sh`** installs the three new units and the nginx config and creates the served folders, enables nothing new, and prints the enable command. `ASTRO_INSTALL_ROOT` and `SYSTEMCTL` let tests run it on a temp folder with a fake `systemctl`; the test refuses a script without them, after a first run of the test (before the script had them) wrote the unit files into this cloud container's own `/etc/systemd/system/` (removed straight after; nothing was enabled).
  9. **Tests:** the deploy on a throwaway git repository and temp site folder, plus `astro web deploy` on this checkout's HEAD; the units by their required keys, `systemd-analyze calendar` for the 15-minute times, and `systemd-analyze verify` with each `Exec` binary's path prefixed by a temp stand-in (nothing else changed); the real nginx config run by conda-forge's nginx with only its CT paths and port pointed at temp folders (`nginx -t`, then requests for the headers, gzip, 304, the 404s and a rollback seen without reload). Without `systemd-analyze` or nginx those tests skip; under CI they fail, and CI installs nginx 1.31.10 with `pixi global` (no lockfile change).

  1. **Assigning to the map grid** (`grid.to_map_grid(values, source, grid)`): each axis on its own, as `nearest_point` does for a place on a regular grid. A map cell centre exactly halfway between two source points takes the southern row and the western column (ties within 1e-9°). Every value is one of the source's own, NaN included; a map cell farther than half a source spacing from the source's outermost point is refused, not given the edge value. Only regular lat-lon sources are taken (MEPS's turned grid is refused; MEPS isn't on the map).   2. **The latest area grids** (`store.areas`, spec Module 6's expiring products): when a global model's run in the map's area (the default saved place's) is processed, the tick also stores, for each verified step over the whole area on the model's own grid, the unrounded total cloud and the Osborn–Sarazin free-atmosphere J with the observer at the model ground (D60 item 1), and the model ground, with provenance (commit, config hash, manifest run id, software). J is stored, never seeing; seeing is computed from J after assignment. One compressed `.npz` per area, model and run under `/staging/forecast/products/areas/<area>/`, written atomically and read back before the run's raw files may go (a file that doesn't read back fails the run); its size counts in the run's derived bytes beside the place files (so the 7-day size report includes it); the newest 2 per model are kept (the one before stays for when the newest fails after storing, as a failed run's area file is removed like its place files). J is computed 6 steps at a time to bound memory. Measured sizes: 12 kB (GFS samples, 5 × 5 points × 49 steps) and 121 kB (ICON-EU samples, 17 × 17 × 49); a full ICON-EU box is about 10 MB by that ratio [estimate] (19 MB with incompressible random values).

The Sun's position is asked of Skyfield once for all distinct times of all the grid's Nights (about 6000 for the box against 234 000 one meridian at a time), and `sun_track` now goes through the same code for one cell.

     - `clear_left` uint8: `tonight()`'s clear hours; 254 when every counted hour left is incomplete ("all incomplete"), 255 when no counted hour is left ("no counted hours"); `counted_left` and `incomplete_left` uint8 are `tonight()`'s n and k (0 for a 255 cell);
     - `dark_left_min` uint16: the minutes of the cell's 1-minute Sun scan in Tonight, from `now` on, with the Sun below −18°; checked against Skyfield's almanac to 2 minutes. It is 0 on a night without dark time (the counted-hours fallbacks of D48 item 2 don't apply to it);
     - `seeing_fa_<family>` uint16: `tonight()`'s seeing range per family in milli-arcsec (scale 0.001, units arcsec), 65535 = none, so a stale family or one without J over the counted hours shows none;

A stale run's cloud is shown, as in the table;
     - `model_ground_<family>` int16: whole metres, half up; −32768 = the family has no stored run (the spec names no code).
     - Rounding is half up; a value that doesn't fit below its code (seeing ≥ 65.535″, a ground outside int16) is an error, never clipped. Every global family of the area has its three layers even with no run, so the page's model picker is stable; MEPS has none and changes nothing.

Each tick records the map's time and size in its report (`map_seconds`, `map_bytes`) and logs them; the CT trial (F1-21) measures them on the real box. The layers of the full box are 2.28 MB a set uncompressed (each uint8 layer 25.6 kB, uint16/int16 51.2 kB, each hour-slider layer 614 kB); since the cells' dark minutes and current hour move on, almost every tick writes a new set (as D84 item 5 already found for the place file), of which 3 are kept.
